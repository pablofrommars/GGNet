## Standing question — do the custom Buffers earn their keep? (added 2026-07-06)

`GGNet.Buffers` (`BufferBase<T>`/`Buffer<T>`/`SortedBuffer<T>`, ~25 use sites) predates this effort: a paged `T[][]` that grows without copying elements and whose `Clear()` keeps pages allocated — designed for the streaming/redraw case where shape buffers are cleared and refilled every render pass. The question to answer as the architecture track proceeds: **does that design still buy anything a BCL collection doesn't, or is it maintenance surface?** Default is BCL unless measured otherwise.

The honest starting scorecard:

- `Buffer<T>` vs `List<T>`: `List<T>.Clear()` also keeps capacity, so the refill case only pays copy-on-grow until capacity stabilizes (first render). After that the paged design buys nothing, and `List<T>` gets span-based enumeration and `Array.Copy` internals. `Buffer<T>` is likely strictly dominated.
- `SortedBuffer<T>` vs `List<T> + BinarySearch/Insert`: SortedBuffer finds the insertion point by *linear scan* and shifts element-by-element across pages; the BCL pattern is O(log n) compares plus one `memmove`. Same asymptotic shift cost, much better constants, far less code — and this week's SortedBuffer corruption bug is the maintenance cost made visible. Dedup-on-equal is the only bespoke semantic (one `if` around `Insert`).
- `Source<T> : Buffer<T>` is the public streaming entry point (3 of the 63 exported types are this chain: `BufferBase`, `Buffer`, `Source`). If `Buffer<T>` goes, `Source<T>` wraps `List<T>` behind its existing `IReadOnlyList<T>` face and the exported surface shrinks by two types.

Checkpoints through the session plan:

- ~~**Session A (explicit pipeline)**~~ — answered (2026-07-06): with the pipeline landed, every `SortedBuffer` use is per-pass state; `SortedBuffer` is reimplemented as a ~40-line BCL-backed wrapper (`List<T>` + `BinarySearch` insert/lookup, dedup-on-equal, key-preserving indexer set for Area's stacking) — the paged `BufferBase` machinery, the linear-scan insert and the cross-page shift loop are gone. Gallery byte-identical. The BCL offers no single sorted+distinct+indexed type, so a thin wrapper is the honest endpoint, not raw `List<T>` at every site.
- **Sessions B–C (grid composition, layout extraction)**: geom `Layer` buffers (`Buffer<IShape>`) become scene primitives; when the compose stage is introduced, accumulate into `List<T>` there rather than porting `Buffer<T>` forward. *(B held to this: `GridComposition` accumulates into `List<T>`.)*
- ~~**Session D**~~ — **question closed** (2026-07-06): `Buffer<T>`/`BufferBase<T>` deleted, every site is `List<T>`; `Source<T>` keeps its public face wrapping `List<T>` (exported surface 63→61, manifest re-pinned). `SortedBuffer` stays as the one survivor: BCL-backed, sorted+distinct+indexed which the BCL doesn't offer in one type. Verdict: the paged design earned nothing once state became per-pass; BCL by default was the right call.
- **Gate**: any swap is verified by the gallery (byte-compare) and, if performance is claimed either way, by measuring a render pass — not by aesthetics. *(Held for both swaps.)*

   **Kill the implicit two-pass protocol.** `Render(first: bool)`, `Clear()`, retrain, reshape — a state machine encoded in booleans and side-effect ordering (train before Commit before Shape), enforced by convention across three classes. Two of this week's bugs lived in its shadows: the SortedBuffer corruption survived because re-training mutates persistent state, and `Render(true)` isn't idempotent (calling it twice duplicates panels). An explicit pipeline with typed stage inputs/outputs makes that bug class unrepresentable.

   *Design sketch.* The `first` flag means something different at every site (build panels / skip clearing / clear-then-shape), the faceting path rebuilds panels on refresh while the default path doesn't, reset responsibility is scattered across four owners (context clears position scales, faceting clears itself and panels, geoms clear layers, `ClearAesthetics` the rest), and `Panel.razor` runs a second miniature `firstRender` protocol of its own. Replace with a flagless `Render()`: `Reset()` (one owner — every stateful participant exposes `Reset()`, the pipeline enumerates them) → `EnsurePanels()` (idempotent, builds only if absent — `first` dies here) → `Validate → Train → CommitAesthetics → BuildLegends → Shape → CommitPositions → MeasureAxes`. Deliberate properties: idempotent (render-twice-identical becomes a test, guarding the duplicate-panels bug), uniform reset (clearing empty state is free, so unconditional), and no persistent trained state — `DiscretePosition` rebuilds its values each pass, deleting the append-across-passes invariant the SortedBuffer bug hid behind (reintroduce persistence only if a streaming case proves hot, as a documented optimization). `Init(bool grid)`/`Initialized` fold into pipeline config. Checkpoint-sized, independent of items 1–2, and doing it first makes item 2 easier: with named stages, the compose boundary is just "everything after Shape". The full dissolution — nothing persists between renders at all — is item 4's spec/realization split.

### A → A+ (library-ambition territory — probably not worth it while self-consumed)

4. **Split specification from realization.** The deepest ggplot2 idea the port skipped: an immutable plot *description* built by the fluent API, realized per render. `PlotContext` is currently builder state + trained state + layout aggregates + orchestration in one mutable object. The split enables safe re-render/concurrency and spec serialization, and dissolves item 3 as a side effect — but touches everything.
5. **A real layer model.** ggplot2's layer = data + stat + geom + position, each swappable. GGNet bakes stats into geoms (Violin owns its density math, Hex its binning). A+ means stat_bin + geom_bar composes into a histogram instead of writing a Histogram geom.
6. **Define the interactivity seam.** No inverse transform (`Unproject(px, py)`) and no hit-test layer beyond browser events. Pan/zoom/brush need pixel→data; an A+ architecture has the seam designed so the feature is additive when a dashboard wants it.

Recommendation: do 1–3 as the architecture track (each compounds with the actual roadmap: arc geometry, PNG export, more coordinate systems); treat 4–6 as out of scope unless GGNet grows consumers beyond its author.

6. **Overload families guaranteed consistent.** The 4–6 hand-copied overloads per geom are the DSL's single source of untruth: nothing prevents a default drifting between the PanelFactory and PlotContext variants. A source generator emitting the family from one per-geom spec fixes this *and* the maintainability cost in one move — it is the same item as the BuilderExtensions split, graduated.

### A → A+ (the DSL as a product)

7. **The DSL teaches itself at the call site.** Revisit the no-XML-docs convention *for the public builder surface only*: for a DSL consumed through IntelliSense, parameter docs are the manual — ggplot2's help pages are half of why its grammar is learnable. Pair with error messages that say what to do next (the sourceless-plot guard is the pattern; apply it everywhere a plot can be mis-assembled).
8. **The DSL's rules are machine-enforced.** A small Roslyn analyzer shipping with the package: warn on positional arguments beyond the selectors, warn on setting both `_color` (mapping) and `color` (constant) for the same aesthetic. The conventions stop being folklore or even documentation — they become squiggles.
9. **The per-geom spec becomes the contract.** Once item 6's generator exists, its input spec (geom × aesthetics × defaults) is effectively a serializable grammar definition — the same artifact can emit the overloads, the README aesthetic matrix, and the F# surface the README promises but nothing verifies.

Recommendation: hygiene items 1–5 are an afternoon combined; API items 1–2 are worth doing in the same breaking-changes window as `Set`→`Commit` (before the 2.0.0 tag), 3–4 opportunistically, 5–6 only alongside a decision to treat GGNet as a public product again. The A+ tiers of both tracks are listed for completeness: they describe a library whose quality is self-enforcing and whose DSL is a documented, analyzable contract — justified by a contributor community, not by a single consumer.
